# تكامل ATLOS — إطلاق SOLO الرقمي

## كيف يعمل الدفع

ينشئ العميل المسجّل طلبًا رقميًا عبر `create_order_atomic`. يحسب الخادم السعر من قاعدة البيانات ويتحقق من المنتج والباقة والمخزون. لمنتجات الأكواد الفورية، يحجز trigger الموجود في `main` أكواد المنتج والباقة المطلوبة داخل معاملة الطلب نفسها؛ إذا لم تكفِ الأكواد تُلغى المعاملة ولا يبقى طلب مدفوع أو مخزون مخصوم.

يتحقق `atlos-webhook` من توقيع HMAC-SHA256 على الجسم الخام، ثم يطابق التاجر والطلب والعملة والمبلغ والحالة ويمنع تكرار Transaction ID. لا يُعتمد الدفع إلا بعد تحقق الخادم. إذا تجاوز المبلغ المدفوع إجمالي الطلب، يسجل webhook الحدث غير المعالج للمراجعة ولا يحول الطلب إلى `captured`. بعد الدفع لا يسلّم المتجر الأكواد تلقائيًا: يراجع المدير الطلب ويكمله من لوحة الإدارة؛ ويجب تسجيل ملاحظة للشحن المباشر أو الخدمة اليدوية.

## حالة التغيير للمراجعة

- أُنشئ فرع محلي مستقل `review/production-readiness-integration-20261111` على أساس `main` لدمج مراجعة الإطلاق الرقمي مع تكامل Paymento وحل تعارض الملفات المشتركة. لم يُدفع هذا الفرع إلى GitHub في هذه الجلسة، وتظل PRs الأصلية دون تعديل.
- لم تُدمج التغييرات إلى `main`، ولم تُنشر Edge Functions، ولم تُطبّق أي migration.
- لم يُغيّر أي سعر أو كود مخزون موجود، ولم تُجرَ معاملة دفع حقيقية أو اختبارية.
- يبقى `store_settings.checkout_enabled = false` إلى حين مراجعة المالك واعتماد خطوة الإنتاج صراحةً.
- لا تظهر منتجات CJ المادية في واجهة الإنتاج، وتبقى وسائل الدفع اليدوية معطّلة.
- واجهة الدفع تعرض الدولار، وهو أساس حساب ATLOS.

## الأسرار وإعداد ATLOS

يجب حفظ `ATLOS_API_SECRET` و`ATLOS_MERCHANT_ID` في **Supabase Edge Function Secrets** فقط. لا تضع السر في GitHub أو Cloudflare Pages أو أي متغير يبدأ بـ`VITE_`. يعيد `checkout-status` معرّف التاجر العام فقط عندما تكون بوابة ATLOS وإعداد webhook جاهزين.

عنوان الإشعار هو:

`https://<project-ref>.supabase.co/functions/v1/atlos-webhook`

يُسجّل هذا العنوان في لوحة التاجر بعد المراجعة. لم تُضبط أسرار الإنتاج أو إعدادات التاجر ضمن هذا التغيير.

## ما يلزم قبل فتح الدفع

1. مراجعة الفرع والمعاينة واعتماد الواجهة ومسارات الطلب، مع إبقاء التغيير غير مدموج حتى موافقة المالك.
2. الحصول من ATLOS على تأكيد مكتوب لبيئة Sandbox أو حساب اختبار ووسيلة التحقق من إشعار الاختبار. لا تستخدم دفعة حقيقية للاختبار.
3. بعد الموافقة، حفظ الأسرار الخادمية وتسجيل عنوان webhook في لوحة التاجر؛ لا تضع أي سر في المتصفح أو Cloudflare Pages.
4. في بيئة اختبار منفصلة، اختبر التوقيع الخاطئ، تكرار Transaction ID، الطلب غير المعروف، اختلاف التاجر أو العملة، المبلغ الناقص والزائد، انتهاء حجز المخزون، وحجز/تحرير الأكواد وتسليمها دون استخدام مخزون الإنتاج.
5. أضف مصالحة دورية لمعاملات ATLOS وإجراءً واضحًا للمدفوعات التي تتطلب مراجعة يدوية. أحداث المبلغ الزائد تُسجل غير معالجة، لكن لا توجد بعد مصالحة مجدولة أو شاشة تشغيلية مخصصة لهذه الحالات.
6. بعد اجتياز الاختبارات والمراجعة، تُنشر الواجهة والوظائف والمigrations المطلوبة ثم يُفتح `store_settings.checkout_enabled` بموافقة المالك الصريحة. لا يُفعّل هذا الخيار في فرع المراجعة.

## الملاحظات المتبقية

إعادة إرسال حدث ATLOS موقّع لكنه غير مطابق لا تعيد تقييمه آليًا؛ قد يظل الدفع الحقيقي المتأخر أو الملتبس في سجل المراجعة حتى تتم المصالحة اليدوية. كذلك يلزم تأكيد Sandbox من ATLOS قبل إجراء اختبار مالي. تسجيل البريد/Google وإعداد روابط Auth الحية لم يُختبرا. استعادة كلمة المرور وTelegram وتذاكر الدعم والعملات المحلية وتبديل اللغة ورفع الصور إلى Storage ليست ضمن ميزات الإطلاق الجاهزة؛ لا تعرضها كميزات عاملة.
